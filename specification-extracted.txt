3. Background Essentials (Brief)

3.1 Voronoi diagrams
Given a set P of n distinct points in the plane, called sites, the Voronoi cell of a site p consists of all points at least as close to p as to any other site, and the Voronoi diagram Vor(P) is the subdivision of the plane into these cells:
Vor(p) = { q ∈ ℝ² : |q − p| ≤ |q − p′| for every p′ ∈ P, p′ ≠ p }(1)
Four properties bound what a correct implementation must produce: every cell is a (possibly unbounded) convex polygon; every vertex is the centre of an empty circle through three or more sites; the straight-line dual of the diagram is the Delaunay triangulation of P; and cells of sites on the convex hull are unbounded, with the whole diagram degenerating to parallel bisectors when all sites are collinear.
3.2 Fortune’s algorithm in one page
Fortune’s algorithm (1987) computes Vor(P) in O(n log n) time with a horizontal sweep line moving monotonically downwards. Five ideas are enough to implement it, to debug it, and to write about it:
Beach line — the lower envelope of the parabolas that have each already-passed site as focus and the sweep line as directrix. It is x-monotone, consists of arcs separated by breakpoints, and summarises everything still relevant. It must live in an ordered structure supporting locate, insert and delete in O(log n); the choice of structure is yours and must be justified.
Site event — the sweep line reaches a new site; a zero-width arc appears and splits an existing arc in two.
Circle event — three consecutive arcs become tangent to one common circle; the middle arc shrinks to nothing at the circle’s lowest point, a Voronoi vertex is emitted, and edges are completed.
Event queue — a priority queue ordered by sweep position, holding n site events and at most 2n − 5 circle events, which yields the O(n log n) bound.
Output — edges are produced incrementally while unbounded edges are only resolved at the end, so a doubly-connected edge list (or an equivalent per-cell boundary representation) plus a final clip to the bounding box is strongly recommended.
You are not required to re-derive the parabola-intersection formulae in your report. You are required to implement the algorithm correctly, to know why each of the five components above exists, and to justify the data structures you chose for them.

4.1 Core requirement: the algorithm must be built from scratch
The algorithmic core — the beach line, the event queue, the event handlers, and the cell/vertex construction — must be your own implementation, produced with AI assistance. You may freely use standard-utility libraries (containers, mathematics, plotting, GUI frameworks; e.g. std::priority_queue, Eigen, NumPy/SciPy for plotting and numerical utilities only, matplotlib, SFML, Qt, three.js).

4.2 Input and output specifications
Your program must support the following input modes:
File input — a plain text file with one site per line: x y (whitespace- or comma-separated). A sample input file must be included in your package.
Seeded random generation — n sites uniform in the unit square, with a user-given random seed (reproducibility is required for your own test suite).
Interactive input — clicking on the canvas adds sites; double-click or a button triggers computation. (Recommended, not mandatory.)
Your program must produce the following outputs:
Rendering of the complete Voronoi diagram on screen (see 4.3).
Export to a lossless raster or vector image (PNG or SVG), written next to the input or to a user-specified path.
Machine-readable output — for every cell, the ordered list of vertex coordinates (and, for unbounded cells, an explicit ray/endpoint of the clipped edge), written to a text or CSV file.
Console statistics — number of sites, number of cells, number of Voronoi vertices, number of edges, and total construction time.
A batch mode must be provided for automated testing, e.g. voronoi --input sites.txt --output result.png --csv cells.csv, in addition to the interactive mode. Command-line arguments must be documented in the README.
4.3 Visualization requirements
The rendered diagram must show: the Voronoi cells (drawn as closed polygons, with hues alternating or assigned per cell for readability), the input sites (as distinct markers, with indices as labels), and an indication of the bounding box used for clipping unbounded edges.
Optional bonus features (each worth up to 2 marks within Criterion 1 of the rubric): animated replay of the sweep (sweep line, beach line, event queue), and overlay of the dual Delaunay triangulation. Screenshots of the visualization are mandatory report figures (Section 6.3).
4.4 Testing, degenerate cases, and benchmarking
A program that draws plausible pictures is not yet correct. Your package must include an automated test suite (script or test program) that covers:
Brute-force nearest-neighbour validation. For random configurations, sample many query points; for each query point, check that the diagram’s reported nearest site matches the brute-force linear scan over all sites. This checks the cells, not just the vertices.
Empty-circle property check. For each emitted Voronoi vertex, verify that it is equidistant (within epsilon) from its three defining sites, and that no other site lies inside the corresponding circle.
Degenerate configurations, each recorded with an annotated figure in the report: all sites collinear (horizontal, vertical, and a generic slanted line); four or more cocircular sites; a mix of very close sites; duplicate input points; a single site; two sites.
Scale and stress test. n = 100, 1,000, 10,000 sites (seeded), reporting construction time for each; the observed growth should be consistent with O(n log n). Confirm memory behaviour stays linear.
Cross-validation (optional but recommended). Compare your output against a reference implementation (e.g., scipy.spatial.Voronoi used only here, in a script under tests/reference_compare/), reporting discrepancies honestly if any remain.
